## 1. 서버 인프라

### 핵심 원칙
**수집 서버와 추론 서버를 분리한다.** 이 시스템은 데이터를 모으고 다듬는 일만 한다. 모델 학습과 실시간 추론은 별도 환경의 몫이므로, 서버는 고사양일 필요가 없다.

### 기능
- 웹 서비스 호스팅 (프론트엔드 + API)
- 업로드 파일 수신 및 백그라운드 전처리 작업 실행
- 데이터베이스 운영
- 외부 STT API 호출 오케스트레이션

### 주요 내용
| 항목 | 선택 | 근거 |
| --- | --- | --- |
| 보드 | Raspberry Pi 4 (4GB) 이상 | GPU·대용량 RAM이 필요한 작업은 전부 외부로 위임했으므로 충분 |
| OS | Ubuntu Server 24.04 LTS (헤드리스) | 서버 운영 문서·생태계가 풍부. `snapd` 제거로 RAM 확보 |
| 컨테이너 | Docker Compose | 앱 격리 + 서버 이전 시 그대로 옮길 수 있음 |
| 작업 큐 | FastAPI BackgroundTasks | Celery/Redis는 이 규모에 과함. 무거운 작업은 단순 잠금으로 직렬화 |
| 프론트 빌드 | **PC에서 빌드 후 배포** | Pi에서 Next.js 빌드는 30분 이상 소요. 서버에서 빌드하지 않는다 |

> 저사양 서버는 제약이 아니라 선택이다. 사양을 올려야 할 시점이 오면 그것은 "추론 기능을 붙일 때"이며, 그때는 서버를 교체하는 대신 **한 대 더 붙인다.**

## 2. 스토리지

### 핵심 원칙
**원본은 절대 변형하지 않는다.** 특정 모델의 요구 규격(샘플레이트 등)을 마스터 포맷으로 삼는 순간, 그 모델이 낡으면 데이터도 함께 낡는다.

### 기능
- 원본 미디어 보존
- 재생성 가능한 파생물 관리
- Export 산출물 임시 보관

### 주요 내용
```
/data/                     ← USB 저장장치 (SD카드 아님)
├── raw_archives/          # 불변. 업로드된 그대로
├── derived/               # 썸네일, 분할 클립, 추출 오디오 — 언제든 재생성
├── exports/               # 학습용 데이터셋 — 요청 시 생성
└── pg_data/               # PostgreSQL 데이터
```

| 계층 | 백업 | 삭제해도 되는가 |
| --- | --- | --- |
| `raw_archives/` | ✅ 필수 | ❌ 절대 |
| `derived/` | ❌ 제외 | ✅ 원본에서 재생성 |
| `exports/` | ❌ 제외 | ✅ DB에서 재생성 |
| `pg_data/` | ✅ `pg_dump`로 | ❌ |

**SD카드 운용 시:** DB와 미디어는 반드시 USB 저장장치에 둔다. `/var/log`는 tmpfs, 스왑 비활성화, `noatime` 마운트로 SD 쓰기를 최소화한다.

## 3. 데이터베이스

### 핵심 원칙
**PostgreSQL이 유일한 원본(Source of Truth)이다.** CSV·JSONL 같은 학습용 파일을 실시간으로 갱신하지 않는다. 파일에 직접 쓰면 동시 업로드 시 손상되고, 태그를 수정해도 반영되지 않는다.

### 기능
- 메타데이터·태그 저장
- 발화 세그먼트 및 얼굴 검출 결과 관리
- 의미 검색용 임베딩 저장 (pgvector)
- 모든 Export 산출물의 생성 원천

### 주요 내용
| 테이블 | 역할 |
| --- | --- |
| `members` | 가족 구성원. 말투 특성, 입력 모드, AI 활용 제한(예외 시) |
| `collections` | 사건·세션·배경 묶음. **파일이 0건이어도 성립한다** |
| `memories` | 구성원별 기억. 당시 감정 / 현재 평가의 이중 구조 |
| `archive_items` | 모든 자료의 공통 레코드. 생산자와 주제인물을 분리 |
| `utterances` | 음성/영상의 발화 세그먼트. **화자 태깅 단위** |
| `face_references` | 구성원별 기준 얼굴 벡터 (연령대별 다중 등록) |
| `face_detections` | 사진에서 검출된 개별 얼굴 + 매칭 결과 |

**기록보다 기억이 상위에 있다.** 인생의 중요한 사건 대부분은 남은 파일이 없다. `collections`를 파일 없이도 성립하는 사건 단위로 두면, 연결된 기록이 0건인 사건이 그대로 **수집 과제 목록**이 된다.

**pgvector를 두 곳에 재사용한다.** 텍스트 의미 검색(RAG)과 얼굴 벡터 검색이 같은 확장을 쓴다. 별도 인프라가 필요 없다.

> 임베딩 차원은 모델 확정 후 결정한다. OpenAI 1536 / BGE-M3 1024 / 얼굴 512.

## 4. 업로드

### 핵심 원칙
**입력 부담이 곧 수집량을 결정한다.** 완벽한 메타데이터를 요구하면 아무도 올리지 않는다. 필수는 최소한으로 두고, 나머지는 나중에 보완 가능하게 한다.

### 기능
- 다중 파일 드래그앤드롭
- 미디어 타입 자동 판별 및 파이프라인 라우팅
- EXIF/메타데이터 자동 추출
- 백그라운드 전처리 큐 등록

### 주요 내용
| 입력 | 필수 여부 | 처리 |
| --- | --- | --- |
| 인물 | ✅ 필수 | 사진은 얼굴 인식으로 미리 제안 |
| 시점 | ✅ 필수 | EXIF 자동. 없으면 연도만, "확실하지 않음" 표시 가능 |
| 장소 | 선택 | 자유 입력 |
| 컬렉션 | 선택 | 기존 선택 또는 새로 생성 |
| 설명 | 선택 | |
| 🔒 비공개 | 선택 | 켜면 외부 API 전송 차단 (`local_only`) |

**미입력 항목은 실패가 아니다.** `ai_status = pending`으로 두고 아카이브에는 정상 노출한다. 학습 데이터셋에서만 제외된다.

## 5. 음성 파이프라인

### 핵심 원칙
**클로닝 품질의 상한선은 모델이 아니라 원본 녹음이 결정한다.** 잡음 낀 1시간보다 조용한 방에서 녹음한 10분이 낫다.

### 기능
- 포맷 표준화 및 원본 보존
- 발화 구간 검출
- 음성→텍스트 전사
- 문장 단위 클립 분할
- 화자 확정 상태 관리

### 주요 내용
```
[업로드] → [원본 보존] → [16kHz mono 임시 변환] → [Silero VAD]
   → [STT 라우팅] → [클립 분할] → [utterances 저장]
```

| 단계 | 구현 | 비고 |
| --- | --- | --- |
| 변환 | ffmpeg 2-트랙 | 원본 보존 + STT 전송용 16kHz (Whisper 네이티브 스펙) |
| VAD | Silero VAD | `speech_pad_ms` 300~400ms로 첫 음절 잘림 방지 |
| STT (기본) | Groq `whisper-large-v3` | 무료 티어 내. 429 시 지수 백오프 |
| STT (폴백) | 로컬 `whisper.cpp` | API 장애 / `local_only` 항목 / 티어 소진 시 |
| 분할 | Whisper 타임스탬프 × VAD 경계 | 2~10초, `{member}_{0001}.wav` |

**녹음 방식에 따라 후처리가 갈린다.**
- 단독 녹음(1인 인터뷰) → 화자 자동 확정 → `ready`
- 대화 녹음(다인) → 화자 미상 → `pending` → 태깅 작업대에서 문장별 지정

> 화자 태깅이 안 된 대화 녹음도 **RAG 검색용으로는 그대로 유용하다.** 버리지 않는다.

## 6. 동영상 파이프라인

### 핵심 원칙
**변환하지 않고 분해한다.** 저사양 서버에서 트랜스코딩은 현실적이지 않다. 동영상은 세 가지 자산의 결합체로 취급한다.

### 기능
- 원본 무변환 보존
- 오디오 트랙 추출 → 음성 파이프라인 위임
- 썸네일 프레임 추출
- (향후) 프레임 샘플링 기반 등장인물 제안

### 주요 내용
| 구성 요소 | 용도 |
| --- | --- |
| 음성 트랙 | STT 전사 + 목소리 학습 데이터 |
| 프레임 | 얼굴 인식 태깅 + 향후 아바타 학습 |
| 영상 자체 | 가족이 감상하는 콘텐츠 |

**하지 않는 것:** 해상도 변경, 코덱 변환, 압축. 원본을 그대로 두고 필요한 것만 뽑아낸다.

## 7. 이미지 파이프라인

### 핵심 원칙
**태그가 곧 학습 캡션이다.** 아카이브 브라우징을 위해 붙인 인물·연도·장소 태그가 그대로 LoRA 캡션 재료가 된다. 학습 전용 입력을 따로 요구하지 않는다.

### 기능
- EXIF 추출 (촬영일·위치)
- 썸네일 생성
- 얼굴 검출 및 인물 태그 제안
- (Export 시) 캡션 텍스트 생성

### 주요 내용
- **자동 캡셔닝은 서버에서 하지 않는다.** BLIP류 모델은 저사양 서버에 부담이다. 수동 태깅 또는 Export 직전 클라우드 일괄 처리로 대체한다.
- 스캔한 옛날 사진은 EXIF 날짜가 **스캔한 날**로 들어간다. 사용자에게 확인을 요청한다.
- 앨범 사진 촬영 가이드를 UI에 노출한다 (창가 밝은 곳, 형광등 반사 회피, 정면).

## 8. 얼굴 인식

### 핵심 원칙
**자동 태깅이 아니라 제안이다.** AI가 확신을 갖고 태그를 확정하면, 틀렸을 때 아무도 모르게 잘못된 데이터가 쌓인다.

### 기능
- 사진·영상 프레임에서 얼굴 검출
- 구성원 기준 벡터와 유사도 매칭
- 확신도에 따른 차등 제안
- 사용자 확인 결과로 기준 벡터 보강

### 주요 내용
| 유사도 | 동작 |
| --- | --- |
| 높음 (≈0.6+) | 미리 체크된 상태로 제안. 확인만 하면 됨 |
| 애매 | "○○님인가요?" 확인 요청 |
| 낮음/미매칭 | 얼굴 박스만 표시, 인물 선택 요청 |

**모델:** InsightFace `buffalo_s` (ONNX Runtime, CPU). 사진 1장당 1~3초. 백그라운드 처리이므로 지연 무관.

**이 프로젝트 특유의 난점**

| 난점 | 대응 |
| --- | --- |
| 나이 변화 (20대 ↔ 80대) | 인물당 **연령대별 기준 벡터 다중 등록** (`era_label`) |
| 옛날 사진 화질 (흑백·노이즈) | 검출 실패를 정상으로 간주, 수동 폴백 |
| 가족 간 닮음 | 임계값 보수적 설정 + 확인 절차 필수 |

**부수 효과:** 얼굴 크롭이 자동 축적된다. 향후 LoRA·아바타 학습 자산으로 그대로 쓴다.

**프라이버시:** 얼굴 임베딩은 생체정보다. 전 과정 로컬 처리, 외부 전송 없음.

## 9. 텍스트 파이프라인

### 핵심 원칙
**말투를 고치지 않는다.** 맞춤법 교정, 문장 다듬기는 페르소나 학습에 해가 된다. 사투리와 습관적 표현이 그 사람의 정체성이다.

### 기능
- 웹 직접 입력 또는 파일 업로드
- 임베딩 생성 (의미 검색용)
- Q&A 쌍 자동 구성

### 주요 내용
- **데일리 인터뷰 답변**은 질문이 이미 DB에 있으므로 `user`/`assistant` 짝이 자동 완성된다. LLM 학습에 가장 이상적인 형태.
- **일기·편지 등 자유글**은 화자 발화 코퍼스로 활용한다.
- 종이에 쓴 글은 사진으로 올려도 된다 (이미지로 보관 + 필요 시 수동 전사).

## 10. 태깅 시스템

### 핵심 원칙
**사람이 확인한 것만 학습에 쓴다.** AI가 추정한 태그와 사람이 확정한 태그를 반드시 구분한다.

### 기능
- 화자 태깅 작업대 (발화 세그먼트별 인물 지정)
- 얼굴 태그 확인·수정
- 학습 적격 상태 관리

### 주요 내용
**`ai_status` — 학습 적격 상태**

| 값 | 의미 | 아카이브 노출 |
| --- | --- | --- |
| `ready` | 화자 확정 + 품질 충족. 데이터셋 포함 | ✅ |
| `pending` | 화자 미태깅, 검수 대기 | ✅ |
| `excluded` | 본인 요청, 품질 미달, 민감 기록 | ✅ |

**`subjects_tagged_by` — 태그 출처**
- `user`: 사람이 확인 → 학습 사용 가능
- `auto`: 얼굴 인식 추정 → **`ready`로 승격하지 않음**

> 원칙: 학습에 못 쓰는 자료도 아카이브에는 남는다. 두 계층은 별개다.

**`answered_by` — 기억 메타데이터의 출처**

`emotion_then`, `evaluation_now`, `motive`는 **본인만 답할 수 있는 값**이다. 가족이 추측해서 채우면 "그 사람의 해석"이 아니라 "가족이 상상한 그 사람"이 되고, 그대로 학습시키면 페르소나가 왜곡된다.

- `self`: 본인 답변 → 페르소나 학습 사용
- `family`: 가족 추정 → 아카이브·RAG에만 사용

비어 있는 것은 결함이 아니라 **아직 여쭤보지 않았다는 표시**이며, 그대로 인터뷰 과제가 된다.

## 14. 백업

### 핵심 원칙
**기능이 아니라 전제 조건이다.** 이 데이터는 대체 불가능하다. 백업이 없는 상태로 운영을 시작하지 않는다.

### 기능
- DB 덤프 정기 백업
- 원본 미디어 증분 동기화
- 자동 복원 검증
- 재해 복구

### 주요 내용
| 대상 | 방법 | 주기 |
| --- | --- | --- |
| DB | `pg_dump` → gzip → 업로드 | 하루 3회 |
| 원본 미디어 | rclone `copy` | 매일 야간 |
| 검증 | 임시 DB에 덤프 적용 | 매월 1일 |

**설계 판단**

| 결정 | 이유 |
| --- | --- |
| `sync` 아닌 `copy` | 로컬에서 실수로 지워도 원격 백업은 보존 |
| `derived/`·`exports/` 제외 | 재생성 가능. 용량·시간 절약 |
| crypt 암호화 필수 | 가족의 사적 기록을 남의 서버에 평문으로 두지 않는다 |
| 임시 DB로 검증 | 운영 DB 무영향으로 백업 유효성 확인 |

> ⚠️ **암호화 비밀번호를 잃으면 백업 전체를 복원할 수 없다.** 서버 밖에 별도 보관한다.

## 16. 페르소나 AI (향후)

### 핵심 원칙
**파인튜닝은 말투를 배우지, 기억을 배우지 않는다.** 이 구분을 놓치면 AI가 없던 추억을 지어내고, 가족이 그것을 진짜로 믿게 된다.

### 기능 (별도 환경에서 수행)
- 말투 재현
- 기억 검색 및 근거 기반 답변
- 목소리 합성

### 주요 내용
| 담당 | 방법 | 결과 |
| --- | --- | --- |
| 말투·성격 | 대화 데이터 LoRA 파인튜닝 | "그 사람처럼 말한다" |
| 실제 기억 | pgvector RAG 검색 | **실제 기록에 근거한 답변만** |
| 목소리 | GPT-SoVITS 등 클로닝 | "그 사람 목소리로 들린다" |

**대체 불가능한 데이터는 '해석'이다**

"1962년 결혼했다"는 호적에도 있다. "그땐 죽을 만큼 힘들었는데 지금 보면 내 인생 최고의 기회였다" — 이것은 본인에게서만 나온다. `emotion_then`과 `evaluation_now`의 **간극이 곧 그 사람의 해석 방식**이며, 목소리나 얼굴과 달리 복제할 수 없는 유일한 자산이다. 단순 Q&A 쌍보다 밀도가 높다.

**환각 방지 설계**
- 검색된 아카이브 내용에 근거하지 않은 답변을 금지한다.
- 관련 기록이 없으면 "기억이 잘 안 난다"고 물러서게 한다.
- 답변마다 **출처 기록을 표시**해 실제 발언과 생성물을 구분한다.

**완성 순서:** 목소리(30분) → 기억 검색(몇 시간) → 말투(500~1,000턴, 약 1년)

**솔직한 한계:** 목소리는 놀랄 만큼 비슷해진다. 그러나 새로운 상황에 대한 판단, 표정, 침묵, 상대에 따라 달라지는 태도는 텍스트에 담기지 않는다. 잘 만들어도 **"닮은 무언가"이지 그 사람은 아니다.** 이는 기술 발전으로 해결될 문제가 아니라, 데이터에 없는 것을 복원할 수 없다는 구조적 한계다.

## 17. 운용 원칙

### 핵심 원칙
**가족이 가족의 기록을 모으는 일이다.** 앨범을 정리하고 어르신의 이야기를 녹음하는 것과 다르지 않으므로, 수집과 활용에 별도의 동의 절차를 두지 않는다. 동의는 전제로 두고 시작한다.

### 기능
- 활용 제한 기록 (예외 발생 시)
- 민감 자료 격리
- 생성물 표시

### 주요 내용
- **기본은 전체 허용.** `members.ai_optout`은 NULL이 기본값이며, 본인이 특정 범위를 원치 않는다고 밝힌 경우에만 기록한다. 동의를 받는 절차가 아니라 **예외를 담아두는 자리**다.

| 값 | 의미 |
| --- | --- |
| `NULL` | 제한 없음 (기본) |
| `voice` | 음성 합성에는 사용하지 않음 |
| `persona` | 대화형 페르소나에는 사용하지 않음 |
| `all` | AI 활용 전체 제외 (아카이브 보관·열람만) |

- **`local_only`는 동의와 무관한 보안 조치다.** 유언·재산·건강 등 민감한 기록이 외부 STT·캡셔닝 API로 나가는 것을 막는다. 증빙 계열(`vital`/`official`/`financial`/`medical`)은 기본 활성화된다.
- **생성물에 "AI 생성" 표시를 남긴다.** 몇 년 뒤 "이게 실제 목소리인가 합성인가"를 판별할 수 없으면 아카이브 전체의 신뢰가 무너진다. 이는 윤리 문제이기 이전에 **데이터 무결성 문제**다.
- **정의를 분명히 한다.** 이 시스템은 "그 사람의 대체물"이 아니라 **"그 사람이 남긴 이야기에 접근하는 도구"**다. 가족이 결과물을 어떻게 받아들일지를 좌우한다.
- 가족 외부로의 공유·공개는 성격이 다른 문제이므로 그 시점에 별도로 판단한다.

## 18. 검토했으나 채택하지 않은 것

향후 재검토를 위해 판단 근거를 남긴다. (참고: 류한조, 「개인 생애기억 아카이브를 이용한 개인서사 구성 연구」, 기록학연구 67, 2021 / 최유리·임진희, 「개인기록 관리 방안 연구」, 기록학연구 47, 2015)

| 항목 | 판단 | 근거 |
| --- | --- | --- |
| 생애서사 플롯 5유형 + 5막 자동 배치 | **미채택** | 감정·평가·동기가 촘촘히 채워져야 작동하는데 우리 환경에서는 성기게 입력된다. 또한 시스템이 남의 인생을 "희생 플롯"처럼 분류해 제시하는 것은 가족 간 불편을 만들 수 있다 |
| TICES 질문 구조 | 미채택 | 임상 트라우마 도구로, 부정적 기억을 체계적으로 파고드는 설계다. 비전문가가 어르신께 사용하기에 위험하다. **감정 어휘만 차용** |
| 시퀀스 / 핵-위성 사건 구분 | 보류 | 개념은 타당하나 입력 부담이 크다. 데이터가 쌓인 뒤 재검토 |
| 사후 기록 관리자 지정 | 미채택 | 가족이 함께 쓰는 시스템이므로 승계 지정이 불필요 |
| 사전 동의 절차 (opt-in) | 미채택 | 가족이 가족 기록을 모으는 일에 형식적 절차는 과하다. 동의를 전제로 하되 **예외만 `ai_optout`에 기록**하는 방식으로 전환 |
| 8단계 생애구분 계층 | 부분 채택 | 별도 계층으로 두지 않고 **타임라인 구간 표시로만** 사용 |

> 정교한 설계가 좋은 시스템을 만드는 것이 아니라, **실제로 쓰이는 시스템이 좋은 시스템**이다. 입력 부담을 늘리는 항목은 그만한 값어치가 확인될 때만 추가한다.

## 부록: 무엇을 먼저 할 것인가

시스템은 나중에 얼마든지 고도화할 수 있지만, **기록할 기회는 지나가면 돌아오지 않는다.**
서버 완성을 기다리지 말고 오늘 스마트폰으로 30분을 녹음하라.
그 파일은 어떤 하드웨어를 쓰든, 어떤 모델이 나오든 그대로 쓸 수 있다.
